# Decisions

Each entry says what was decided and why. Sources for the technical facts are numbered rows in [SOURCES.md](SOURCES.md) (S1, S2, ...).

## Structure and tooling

**D-01. Logic in Swift package targets, a thin app target.** `WaveContainer`, `MelFrontEnd`, `StemInspectorCore` and `StemInspectorUI` are package targets; the Xcode app target holds one file that wires the real `FileWorker` into the window. The libraries, the file worker and the screenshot test run with `swift test`; the view-model unit tests, which use an in-memory file service and no disk, run in the app's test target under `xcodebuild test`.

**D-02. macOS CI is the only compiler.** The authoring machine runs Windows and cannot build Accelerate, AppKit or SwiftUI code. No Swift toolchain was installed on Windows. Changes were batched; every result in this repository comes from a GitHub-hosted `macos-latest` runner (S48). The run history, including failures, is in D-25.

**D-03. Swift 6 language mode everywhere.** `swiftLanguageModes: [.v6]` in Package.swift (S28) and `SWIFT_VERSION = 6.0` in the Xcode project (S41), which makes strict concurrency checking complete (S27, S41). Value types are `Sendable`; the only reference types holding state are the `@MainActor` view model, the `FileWorker` actor, and internal helpers used on one thread inside a single call (the file reader and the XML tree builder).

**D-04. Tests use Swift Testing** (S30), including parameterised tests for the spec examples and edit cases. Package tests run in the release configuration with testing enabled (`-c release -Xswiftc -enable-testing`) so the 4 GiB integrity hashes and the fuzz loops run optimised; every CI run builds the `@testable` test targets this way.

## Container library (WaveContainer)

**D-05. One parser for RIFF, RF64 and BW64.** The header id selects the container; for RF64 and BW64 the first chunk must be `ds64` (S1). A 32-bit size of `0xFFFFFFFF` takes its value from `ds64`: the data size for `data`, otherwise the next unused table entry with the same id (S2, S3). The walk stops at the declared end or the file end, whichever comes first, as the Python reference does, and bytes after the last chunk are kept as trailing bytes.

**D-06. The audio payload is never loaded.** Reads use `FileHandle` seeks and exact-length reads (S16). Only metadata chunks are loaded, each checked against a 16 MiB limit before allocation; other limits cap the chunk count (10,000), the `ds64` table (1,024 entries), and for iXML flattening the nesting (64 levels), the element count (100,000) and the bytes of flattened keys and values (64 MiB). Every index into file-derived bytes goes through a bounds-checked reader or follows an explicit length check; the library has no force unwrap, `try!` or `fatalError`.

**D-07. bext text is ISO 8859-1 with trailing NUL bytes removed**, matching the reference, so every byte maps to one character and an unchanged field writes back byte for byte. The number of NUL bytes after the coding history is kept, so editing a fixed-width field never changes the size of the chunk, and a coding history edit uses that NUL space first (S6).

**D-08. Loudness values are `Decimal`, rounded with `.plain`.** Tech 3285 v2 defines the rounding on decimal values (S8). A binary double cannot hold 1.005, and 1.005 x 100 evaluates to just below 100.5 (the test prints the value as `DOUBLE` in the CI log), which a naive rounding takes the wrong way; the API takes `Decimal` and rounds half away from zero with `NSDecimalRound(..., .plain)` (S12). The six specification examples are tests. Note on the reference: its source comment gives 12.765 x 100 as an example of binary noise, but on the CI runner 12.765 x 100.0 evaluates to exactly 1276.5 (the first version of our test asserted the opposite and failed, run in D-25); our test now uses 1.005.

**D-09. Version rule.** Reading never changes a chunk. Setting a loudness field to a measurement raises `Version` to 2, because the loudness fields exist from Version 2 on (S7); in Versions 0 and 1 those ten bytes are reserved zeros, so on that raise the other four fields are set to 0x7FFF ("not used", S9) instead of reading as measurements of 0.00. Setting `Version` back to 0 or 1 is refused while a measurement is stored and otherwise zeroes the reserved bytes. `specificationIssues` reports non-zero reserved bytes and out-of-range loudness values.

**D-10. Two write paths, chosen per write.** A symbolic link is resolved first, so both paths act on the real file.
- *In place* when the new chunk fits the old one's space: exactly (header, payload and pad); or with a `JUNK`, `PAD ` or `FLLR` chunk directly after it growing or shrinking to absorb the difference; or, when it is smaller by at least 8 bytes, with a new zero-filled `JUNK` chunk in the rest of the old space. Before writing, the planned byte range is checked against the audio range and the write is refused if they overlap.
- *Streaming rewrite* otherwise: the file is streamed in 1 MiB blocks into a hidden temporary file in the same directory, synchronised, parsed again, its data size compared with the original and, with verification on (the default), its audio hash too; only then is it swapped in with `FileManager.replaceItemAt` (S15). On any error the temporary file is removed.
- A new bext goes before `fmt `, where the BWF file structure places it (S4); a new iXML is appended at the end. (The Python reference writer puts bext first of all chunks and also moves existing bext and iXML chunks on every write; this writer never moves an existing chunk.) Unknown chunks, chunk order, the pad bytes of unchanged chunks (including non-zero ones) and trailing bytes are copied unchanged; a replaced chunk of odd size gets a zero pad byte. When a chunk is appended after an odd-sized last chunk whose pad byte is missing at the end of the file, the pad byte is written first.

**D-11. The integrity check is public and always on by default.** `AudioIntegrity.dataChunkSHA256` hashes the data payload (not its pad byte). `MetadataWriter.apply` hashes before and after and fails if they differ. Every test that writes in the Metadata writes suite, and the large-file test, call the public check themselves; the duplicate-chunk test, where the write is refused, compares the whole file instead, and the on-disk fuzz test hashes independently of the writer before and after every write. The screenshot test's setup writes rely on the writer's own check. SHA-256 is implemented in the target because the target is Foundation only; it is tested against NIST's SHA-256 example values and additional test data (S14) and against Python `hashlib` digests of all 15 corpus files.

**D-12. Refusals instead of guesses.** A write that would replace a chunk occurring twice is refused (reading uses the last one, as the reference does). A plain RIFF file that would pass 4 GiB is refused instead of converted to RF64.

**D-13. iXML is kept as raw bytes.** Reading never re-serialises it; writing stores the given text as UTF-8 padded with one space to an even length (S11). Flattening for parity rebuilds ElementTree's view with `XMLParser` (S13): an element's text is the text before its first child (S57), attributes, repeated siblings numbered from 1 as the reference does (S55). External entities are not resolved.

**D-14. Command line tool without dependencies.** `stemkit inspect <file> --json`, `set <file> <field> <value>` and `verify <a> <b>`; exit code 0 for success or same audio, 1 for different audio, 2 for errors.

## Mel front end (MelFrontEnd)

**D-15. Exact DFT at length 400 as a matrix product.** Accelerate documents DFT lengths f x 2^n with f in {1, 3, 5, 9, 15} for its interleaved DFT (S25); 400 = 25 x 16 is not supported (a test shows Accelerate refusing 400 and accepting 320), and zero padding would change the frequency grid. The DFT is evaluated from its definition in double precision: cosine and sine tables with the angle reduced exactly in integers, and two `vDSP_mmulD` products per chunk (S26). A test compares it with a naive O(N^2) loop.

**D-16. Reproduce the reference step by step, not approximately.** The port follows the numpy path of transformers 5.18.0 (S20, S21): zero pad or truncate to 30 s; reflect pad by 200 (S22); periodic Hann window computed with numpy's own expression, so the only remaining difference is the platform's cosine (S23); frames in double; the spectrum stored as complex64 as the reference's buffer does; power as the float64 magnitude squared, as the reference's `np.abs(spectrum, dtype=np.float64) ** 2` (S21), here `hypot(re, im)` squared; Slaney mel filters with Slaney normalisation built with the reference's own linspace and formulas; `max(1e-10, x)`, `log10`, cast to float32; drop the last frame; clamp to max minus 8 and `(x + 4) / 4` in float32. Result on CI: every element of all six clips equal to the reference, in run 37376814709 and every run after it (D-25).

**D-17. Pass threshold 1e-6 per element, 2e-7 mean.** The two implementations round to float32 at the same three points, so the only possible differences are values on a float32 rounding boundary that round the other way: at most 2.4e-7 for a flip of a log10 value below 16 in magnitude, plus one output ulp (1.2e-7) in the final step. Most elements of a padded chunk sit on the clamp floor (peak minus 8), so one flip of the peak value would move all of them by about 1.2e-7 at once; the mean bound allows that single event and nothing systematic. The reasoning is in the test's comment; the measured error is zero.

**D-18. Fixtures from pinned versions with torch absent.** `reference/requirements.txt` pins transformers 5.18.0 and numpy 2.5.3; the script refuses to run if torch is importable, because transformers would then use its torch path. Inputs are 16-bit integers divided by 32768 on both sides, which is exact in float32. The corpus covers a sweep, noise bursts, tones, silence, a 300 sample clip and a 35 second clip (longer than one chunk).

## App (Stem Inspector)

**D-19. Deployment target macOS 14.0.** `@Observable` (S32), `@Bindable` (S33) and the SwiftUI APIs used need macOS 14 at most; `Table` needs 12 (S35). Nothing newer is used, so 14.0 is the lowest target the code allows, and the package declares `.macOS(.v14)` (S29).

**D-20. A committed Xcode project, written by hand, no generator.** The project references the package at the repository root as a local package (S37) and lists folders rather than files (its groups are `PBXFileSystemSynchronizedRootGroup` entries), so it stays small. No project generator is needed to build. It was written without Xcode on the authoring machine and validated only by `xcodebuild` on CI, which is the main risk of this choice; the shared scheme is committed so the scheme CI names is defined in the repository.

**D-21. Ad hoc signing with the hardened runtime and an explicit entitlements file.** `CODE_SIGN_IDENTITY = "-"` is ad hoc signing, "Sign to Run Locally" (S42); it needs no account and still embeds the entitlements. `ENABLE_HARDENED_RUNTIME = YES` (S41, S40). The entitlements file contains only App Sandbox (S38) and user-selected read and write access (S39), and nothing for the network. CI reads them back from the built app with `codesign` (S43), converts both the embedded and the committed entitlements to JSON and fails unless each is exactly these two keys set to true. That exact check found that ad hoc signing had added `com.apple.security.get-task-allow`, the debugging entitlement Xcode injects from the platform's base entitlements and that notarisation forbids (S52); the Release configuration now sets `CODE_SIGN_INJECT_BASE_ENTITLEMENTS = NO`, so the Release build carries exactly the committed file. Debug keeps the default so the app can still be debugged.

**D-22. Concurrency design.** The view model is `@MainActor @Observable`. File work goes through the `StemFileService` protocol, so tests inject an in-memory actor and the app injects `FileWorker`. `FileWorker` is an actor because it owns the list of security-scoped URLs (S18); folder expansion runs on the actor, and the file operations (load, save, rename) are `nonisolated async`, so several run at once. Batches run in a `TaskGroup` (S31) with at most four files in flight; results are applied on the main actor as each one finishes, matched to rows by a stable `UUID`, and progress counts up. Cancelling stops scheduling new files. Each file operation runs in its own unstructured task, which has no parent task and so is not reached by the group's cancellation (S56), so a file already being written finishes and is never recorded as a failure. Rows of files that never started are removed, so dropping the items again loads them; rows that failed to load are retried the same way. One batch runs at a time, whichever entry point starts it. Items dropped while a batch runs are queued and load when it ends; Cancel also drops the queue, and a cancel that arrives before the batch starts any file starts none. A save whose write succeeded but whose reload failed is shown as saved, with the reload error on the row. Duplicate files in one drop (a folder plus a file inside it) give one row. Text typed in the inspector during a batch is kept. Before a save or a rename, the view model asks the file service whether it can create files in each folder involved; if not, it asks an injected `FolderAccessRequester` (in the app, an open panel pointed at the folder, which extends the sandbox to what the user selects, S34) and records the grant. Renames in folders still without access are skipped with an error on the row; saves are still tried, since an in-place write needs only the file. Every failure is stored on its row, except a failure to read the dropped items themselves and a drop refused because the table would pass 10,000 files; neither has a row, so both go to the status line.

**D-23. The inspector applies only the fields the user changed.** The first screenshots from CI showed a real bug: with two files selected, changing only the originator also copied the first file's description onto the second. The inspector now compares its fields with the values it loaded and copies only the changed ones; a unit test and the screenshot test check that each file keeps its own description.

**D-24. Screenshots are rendered by a test from real files.** The test writes six WAV files, loads them through the real `FileWorker`, edits and saves two of them (so their badges are real), then renders the real `StemInspectorView` in a borderless window with `NSHostingView`, `bitmapImageRepForCachingDisplay` and `cacheDisplay` (S46), in light and dark appearance. CI uploads the PNG files as the `screenshots` artifact and prints their SHA-256; the files under `docs/screenshots/` are the artifact files of run 37400549002, unchanged (same SHA-256 as printed in its log). Two problems found this way and fixed: the system inspector column rendered as an empty coloured block and dark text vanished on the transparent root (the layout now uses a plain column and an explicit window background), and a titled window was shrunk to fit the runner's screen (the test now uses a borderless window, checks the rendered size and prints it in the log).

**D-26. Repository guards are tests.** `RepositoryGuardTests` scans every text file, itself included, for the em dash, names, contact details and statements of how long work took. The list of names is not in the repository in any form. CI passes it from a repository secret, `STEMKIT_DENIED_NAMES`, as an environment variable (S61); the test compares every lowercase word and word pair with it and reports only positions, never a name. A secret that is not set reads as an empty string (S61), so the CI step stops before testing, and the test also fails on an empty list: the name check cannot pass by being skipped. A pull request from a fork receives no secrets (S61) and fails the same way. CI also checks that the test reported the expected number of entries (`EXPECTED_DENIED_NAMES` in the workflow), so a truncated secret fails too. The secret is stored as one comma-separated line. For the first run of this repository it held one entry per line; the runner masked each line on its own, and the public log showed a short entry masked inside ordinary words, which hints at that entry. GitHub's guidance is that redaction relies on an exact match of the value and that a log exposing a secret should be deleted (S62), so that run's log was deleted and the secret was rewritten as a single line, which ordinary log output does not contain. An earlier version stored the names as unsalted SHA-256 digests. A check found that a digest of a short name can be reversed by hashing likely names until one matches, so the list moved to the secret and the repository was recreated from a single commit, which removed the digests from its history (D-25). The repository's own address, which contains the hosting account's login, is removed before the name check; it is where the code lives, not a statement about a person. The same address appears in the CI run links in TESTING.md, which the brief requires. Decision: keep those links, because the run URL is the evidence the brief asks for; the login is the hosting account's identifier, and the handover flags it so the owner can choose to rename the account or remove the links.

**D-27. Corpus fixtures are copied into this repository.** CI cannot read the private repository that holds the reference module, so the 15 corpus WAV files (about 11 MB) are committed next to the golden JSON, and the manifest records the SHA-256 of each WAV and each JSON file. The Swift test checks every WAV against the manifest with its own SHA-256 before comparing fields.
