# Limits: what is not done, and why

Stated plainly so a reviewer does not have to find them.

## Distribution

- **Not signed with a Developer ID, not notarised.** That needs a Developer ID certificate, which comes with an Apple Developer Program membership (S49 in SOURCES.md). CI signs ad hoc ("Sign to Run Locally") so the sandbox and hardened runtime settings are embedded and checked; that signature is meant for running locally, not for distribution. The exact steps are in [RELEASE.md](RELEASE.md).
- **Built and tested only on the CI runner.** The machine this was written on runs Windows and cannot compile Apple frameworks. Every compile, test and screenshot comes from GitHub-hosted macOS runners; nothing was run on a physical Mac.

## The app

- **No UI automation.** UI tests need a Mac session to record and debug, which this work did not have; the view models are unit tested without disk, the core is tested on disk, and the main view is rendered by a test for the screenshots (in a borderless window, so the window's toolbar is not in the image), but there are no XCUITest flows (clicking, drag and drop, file panels).
- **Sandbox and folder access: designed, not tested in a sandbox.** The app asks only for user-selected read and write access (S34 in SOURCES.md). A streaming rewrite creates a temporary file next to the original and a rename changes the folder, so both need write access to the folder. Before saving or renaming, the app probes each folder and, when it cannot write there, shows an open panel pointed at the folder so the user can grant it; renames in folders still without access are skipped with an error, and saves are still tried because an in-place write needs only the file. The probe, the grant and the skip are unit tested with an in-memory service; the open panel and the real sandbox were never exercised, because the tests run unsandboxed and no sandboxed build was run on a Mac.
- **The app edits five bext text fields and the time reference.** Description, originator, originator reference, origination date and time, and the time reference are editable in the inspector; Version, CodingHistory, the loudness fields, the UMID and iXML are written by the library and the command line tool only, to keep the app's scope to the fields a stem delivery usually changes.
- **Accessibility, localisation and undo** were not addressed; the sample concentrates on file safety and concurrency, and each of these needs design and testing of its own.
- **Multi-selection editing compares with the first selected row.** A field is applied to the selection when it differs from the first selected row's value (unapplied edits are carried across a selection change onto the new row), so setting several files to the value the first one already has needs a second edit. A per-field mixed-value state would remove this; it was left out to keep the inspector simple. A per-field mixed-value state would remove this; it was left out to keep the inspector simple.
- **Long folder scans.** Expanding a dropped folder runs before the batch starts, so it shows no progress and cannot be cancelled (it runs on the file actor before the batch exists; moving it into the batch was not done because it would need its own progress model); loading hashes each payload with synchronous reads on the concurrency pool (at most four at once), and a load in progress is not interrupted by Cancel, because the hash reads are synchronous and a half-read file gives nothing useful.
- **Sandbox access is held.** Access to dropped or chosen items is kept for the life of the app, because a later save or rename may need it; nothing releases it before the app quits. Apple documents that access not given back keeps kernel resources in use and can stop the app adding locations to its sandbox until it is relaunched (S18 in SOURCES.md), so a session with very many separate drops could reach that limit. Repeated grants of the same item are not stacked.
- **Edits made by other programs while the app is open.** A save writes the bext built from what the app loaded plus the inspector's edits; a change another program made to the same file's bext in between is overwritten. Only the audio is compared before and after, because detecting outside edits needs a re-read and a merge rule that this sample does not define.
- **Duplicates through links.** Files are matched by path. The same file dropped through a symlink in one drop and its real path in another, or through a hard link, gives two rows, and saving both writes the file twice. Matching by file identity (as the case-only rename already does) was not extended to drops because it needs a metadata read for every dropped file.
- **Very large tables.** Each row keeps its bext chunk, whose coding history may be up to 16 MiB, and the table holds up to 10,000 files; the naming preview is recomputed whenever the table changes. Neither was measured at that scale, because CI runs use small generated folders.
- **No identification of stems by on-device models.** The product this sample is aimed at does that; this repository covers the file layer and the audio front end such models consume.

## The container library

- **No conversion from RIFF to RF64.** A plain RIFF file whose rewrite would pass 4 GiB is refused with a typed error rather than converted, because a metadata edit that silently changes the container type would surprise a delivery pipeline. The same refusal applies to an RF64 or BW64 file that stores a real 32-bit outer size instead of 0xFFFFFFFF.
- **Pad bytes of replaced chunks.** Unchanged chunks keep their pad bytes exactly, including non-zero ones; a bext or iXML chunk that is replaced and has an odd size gets a zero pad byte.
- **One corpus layout.** All 15 reference corpus files have the same layout (bext, fmt, data, iXML, even sizes, Version 2). Other layouts (odd sizes, pad bytes, filler chunks, RF64 and BW64, ds64 tables, extensible formats) are covered by synthetic files in the tests, not by the Python parity check.
- **In-place writes are not atomic for metadata.** They never touch the audio range (checked before writing), but a crash during an in-place write can leave a damaged bext or iXML chunk. The in-place path is kept because it avoids copying gigabytes of audio for a metadata edit, which is the point of the requirement. The streaming path swaps the file in with one `FileManager.replaceItemAt` call, which Apple documents as ensuring no data loss.
- **iXML namespaces.** Flattening matches the Python reference (ElementTree) for documents without namespaces, such as every file in the corpus; namespaced iXML was out of scope because the parity target has none. For a namespaced document, element names are reported as `prefix:name` where ElementTree reports `{uri}name`.
- **Files over 4 GiB are tested with sparse files.** The parser and the in-place path are proven on 4 GiB plus 2 KiB data chunks without writing the audio; the streaming path is proven on small RF64 and BW64 files only, because a streaming test on a large file would write gigabytes on CI.
- **Fuzzing is deterministic mutation, not coverage guided.** It runs thousands of truncations and bit flips of valid headers with a fixed seed, so failures reproduce, but it is not a substitute for a coverage-guided fuzzer.

## The mel front end

- **Default parameters only.** The parity tests cover the reference's default configuration (80 bins, 16 kHz, hop 160, n_fft 400, 30 second chunks). Other configurations are accepted within bounds that keep memory finite (at most 512 bins, 192 kHz, 60 second chunks, a 4096-point transform and 10,000 frames per chunk, the hop being raised to keep that) but are not compared with the reference, because fixtures were generated for the defaults only.
- **The numpy path of the reference.** Fixtures come from transformers with torch absent, which selects its numpy implementation. transformers documents that numpy path as matching Whisper's original torch implementation within a 1e-5 tolerance; the torch path was not compared here.
- **No resampling or channel mixing.** Input must already be 16 kHz mono float samples, as the reference extractor also expects; choosing a resampler is a separate decision with its own parity question. A non-finite sample inside the frames the reference keeps makes every output value NaN, as it does in the reference.
- **Speed.** The DFT is a direct transform done as a matrix product, chosen for exactness at length 400. The benchmark figure is reported, not optimised.
